# 데이터 갱신과 알림

## 1. 공공 API

| API | 범위 | 주요 정보 | 용도 |
|---|---|---|---|
| 인천 운항 현황 상세 (B551177) | 인천, **D-3 ~ D+6** | 시각, 상태, 터미널, 게이트, 체크인 카운터, 수하물 수취대, 코드쉐어 | 실시간 갱신 |
| 인천 정기운항편 일정 (B551177) | 인천, 현재 시즌 | 편명, 운항 기간, 요일 | D-3 이전 존재 확인 |
| 한국공항공사 운항 스케줄 (B551178) | 인천 외 국제선 | 시각 | 존재 확인 |
| 한국공항공사 실시간 검색 (B551178) | 인천 외, 당일 | 시각, 지연, 결항, 게이트(자료마다 다름) | 실시간 갱신 |

**주의**
- 응답 시각에는 시간대가 없다. **한국 시간(Asia/Seoul)**으로 해석한다.
- 한국 공항 쪽 정보만 나온다. 상대 공항의 시각은 출발·도착 편 응답에 없을 수 있다. 이 경우 비워 두고 사용자 제보를 받는다.
- 한국공항공사 실시간 API는 날짜 조건이 없다. **오늘 날짜 항공편에만** 연결한다.

**구현 전 검증 항목** (개발 키 발급 후)
1. 공항·날짜 단위로 목록 전체를 한 번에 받을 수 있는지(페이지 크기). 가능하면 항공편 수와 상관없이 호출량이 일정해진다.
2. 코드쉐어 응답 구조 (`masterFlightId` 등)
3. 한국공항공사 응답의 게이트·터미널 제공 여부
4. 자정 전후 항공편의 날짜 처리
5. 실제 일일 한도와 초기화 시각

## 2. 조회 주기

| 구간 | 주기 | 사용 API |
|---|---|---|
| 등록 시 | 1회 | 일정 또는 운항 현황 |
| ~ D-3 | 하루 1회 | 일정 (존재·시각 변경 확인) |
| D-3 ~ 출발 6시간 전 | 1시간마다 | 운항 현황 |
| 출발 6시간 전 ~ 도착 + 1시간 | **15분마다** | 운항 현황 |
| 이후 | 중지 (`phase = done`) | |

- 도착 시각을 모르면 출발 + 6시간을 도착 + 1시간 대신 쓴다.
- 결항이 확정되면 출발 시각이 지난 뒤 중지한다.
- `trackerCount`가 0인 항공편, 한국 공항이 없는 항공편은 조회하지 않는다.

## 3. 예약 함수

Cloud Scheduler 무료 작업 3개 안에서 운영한다.

| 함수 | 주기 | 하는 일 |
|---|---|---|
| `pollFlights` | 15분마다 | `nextPollAt`이 지난 항공편 조회 → 변경 감지 → 알림 → Live Activity 시작·갱신 |
| `dailyCleanup` | 매일 04:00 (일본 시간) | 지난 이력·미사용 항공편·호출 기록 삭제 |

### `pollFlights` 처리 순서

```
1. nextPollAt ≤ 지금인 flights 조회
2. (공항, 날짜, 출발/도착) 묶음으로 공공 API 호출  ← 묶음 조회가 되면
3. 응답을 정규화해 기존 값과 비교
4. 바뀐 항목 저장 (source = airport_data)
   - 공항 데이터 값이 생기면 그 항목의 사용자 제보 값을 덮어쓴다 (API 우선)
5. 변경 알림 대상 변경이면 등록 사용자에게 FCM 알림 (사용자 언어로)
6. 진행 중 Live Activity가 있으면 갱신 푸시
7. 출발 3시간 전 구간에 들어온 항공편 → Live Activity 시작 푸시
8. 다음 nextPollAt 계산
```

## 4. 변경 감지

| 변경 | 알림 |
|---|---|
| 출발 예정·변경 시각이 **5분 이상** 바뀜 | 출발 시각 변경·지연 |
| 상태가 결항으로 바뀜 | 결항 |
| 출발 터미널 바뀜 | 터미널 변경 |
| 출발 게이트 `null` → 값 | 게이트 배정 |
| 출발 게이트 값 → 다른 값 | 게이트 변경 |
| 도착 시각이 5분 이상 바뀜 | 도착 시각 변경 |
| 수하물 수취대 `null` → 값 | 수하물 수취대 |

- 한 번의 조회에서 여러 변경이 생기면 **알림 하나로 묶는다.**
- `airport_data` 값이 사라지는 경우(값 → `null`)는 알리지 않고 마지막 값을 유지한다. (API 일시 누락 대비)
- 사용자 제보로 생긴 변경은 감지 대상이 아니다.

## 5. 알림 발송

| 종류 | 보내는 곳 | 방법 |
|---|---|---|
| 변경 알림 | 서버 | FCM. 사용자 `notify.changes`가 켜진 경우만 |
| 임박 알림 | 앱 | 로컬 알림 예약 |
| Live Activity 시작 | 서버 | FCM + `liveActivityStartToken`. `liveActivityEnabled`인 경우만 |
| Live Activity 갱신·종료 | 서버 | FCM + `liveActivityUpdateToken` |

### 임박 알림 예약 (앱)

- 앱 실행, 항공편 변경 감지(Firestore 구독), 설정 변경 때마다 **전체를 다시 예약**한다.
- 기준 시각: 변경 시각이 있으면 변경 시각, 없으면 예정 시각
- iOS 대기 알림 64개 제한 때문에 **가까운 항공편부터 최대 60개**만 예약한다.
- 결항 항공편, 이미 지난 시점은 예약하지 않는다.
- 앱이 오래 실행되지 않으면 시각 변경이 반영되지 않을 수 있다. 이 경우에도 서버 변경 알림은 간다.

### 위젯 데이터 (앱)

- Firestore 구독으로 항공편이 바뀌면 다가오는 항공편 요약을 App Group에 저장하고 위젯 갱신을 요청한다.
- 위젯은 D-Day 계산용 타임라인을 자정마다 넘겨 둔다.

## 6. 호출 한도 보호

공공 API 일일 호출 수를 `system/quota_{날짜}`에 센다.

| 사용률 | 동작 |
|---|---|
| ~ 80% | 정상 |
| 80 ~ 95% | `hourly` 구간을 3시간마다로 늘린다 |
| 95% ~ | `frequent` 구간(출발 6시간 이내)만 조회. 새 검색은 `resource-exhausted` |

실패 시 다음 주기에 다시 시도한다. 연속 2회 실패하면 앱이 '확인 실패'를 표시한다.

## 7. 호출량 추정

항공편 1편의 마지막 3일: 1시간마다 약 66회 + 15분마다 약 40회 ≈ **106회**.

| 키 | 일일 한도 | 항공편 단위 조회 시 하루에 처리 가능한 항공편 수 (대략) |
|---|---|---|
| 인천 개발 키 | 500 | 약 10편 |
| 인천 운영 키 | 100,000 | 약 2,000편 |
| 한국공항공사 개발 키 | 5,000 | 약 100편 |

**출시 전에 인천 운영 한도 신청이 필요하다.** 공항·날짜 묶음 조회가 가능하면 호출량은 크게 줄어든다.
