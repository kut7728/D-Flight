# 데이터 갱신과 알림

## 1. 공공 API

| API | 범위 | 주요 정보 | 용도 |
|---|---|---|---|
| 인천 운항 현황 상세 (B551177) | 인천, **D-3 ~ D+6** (2026-10-12 확인) | 시각, 상태, 터미널, 게이트, 체크인, 수하물, 코드쉐어 | 실시간 갱신. 출발·도착 각 1회로 하루 전체 |
| 인천 정기운항편 일정 (B551177) | 인천, 현재 시즌 | 편명, 기간, 요일, 시각(HHMM) | D-3 이전 존재 확인. 코드쉐어 없음 |
| 한국공항공사 운항 스케줄 (B551178, 15158949) | 인천 외. 날짜로 그 날 유효한 스케줄 | 요일, 시각(HHMM), 기간 | D-3 이전 존재 확인. 코드쉐어 없음 |
| 한국공항공사 `flight-status/arrival`, `/depart` | 인천 외, **D-3 ~ D+6** | 시각, 지연, 결항, 코드쉐어 | 묶음 갱신. 게이트·터미널 없음 |
| 한국공항공사 `flight-status/info` | 공항·출도착·국내국제 묶음. 날짜 파라미터 없음. 시각은 HHMM | **게이트**. 터미널·수하물 없음 | 당일 게이트. 한 페이지 100건, 넘으면 다음 페이지 |
| 한국공항공사 `flight-status/detail` | 공항 필터 없음. 표본 날짜는 전날·당일·다음날 | 게이트, 수하물, 비행일자 | 갱신에 쓰지 않음. 100건씩이고 1,000건 요청은 실패 |

**주의**
- 응답 시각에는 시간대가 없다. **한국 시간(Asia/Seoul)**으로 해석한다. 운항 현황 시각은 `YYYYMMDDHHMM`이라 날짜가 포함된다. 조회일에 맞추지 말고 이 값의 날짜를 쓴다.
- 한국 공항 쪽 정보만 나온다. 상대 공항의 시각은 비워 두고 사용자 제보를 받는다.
- 인천 터미널 코드: `P01` 제1여객터미널, `P02` 탑승동, `P03` 제2여객터미널. 여객편 응답에서는 이 세 값만 나왔다.
- 인천 코드쉐어는 `Master`(운항 편, `masterFlightId` 비움)와 `Slave`(코드쉐어, `masterFlightId`에 운항 편명). 한국공항공사는 `Y`일 때만 `masterflightid`가 운항 편명이다. 일정 API에는 코드쉐어가 없으므로 D-3 이전에는 입력 편명으로 두고, 운항 현황이 나오면 운항 편명 문서로 합친다.
- 한국공항공사 게이트는 `flight-status/info`에 있다. 2026-10-12 김포 국제선 출발·도착은 게이트가 모두 채워져 있었다. 시각은 HHMM이라 당일 한국 시간으로 본다. 터미널 필드는 없다.
- `flight-status/detail`에도 게이트·수하물이 있다. 공항으로 거르지 못하고, 한 페이지가 100건이라 전체를 받으려면 호출이 수십 회다. 다음날 표본의 게이트는 비어 있었다. 갱신에는 `/info`만 쓴다.
- 인천 출발 게이트는 당일에는 거의 채워져 있었다. D+6 표본은 비어 있었고 체크인 카운터는 채워져 있었다.

### M1에서 확인한 호출 방식 (2026-10-12)

실제 응답은 저장소에 넣지 않았다. 구조만 기록한다.

1. **묶음 조회 된다.** 인천 도착 1,201건, 출발 1,189건을 `numOfRows=2000` 한 번에 받았다. 한국공항공사도 공항·날짜 목록이 한 페이지에 들어온다. 호출량은 항공편 수가 아니라 (공항, 날짜, 출발/도착) 묶음 수에 비례한다.
2. **날짜 범위.** 조회일 D-4·D+7은 0건, D-3·D+6은 데이터가 있었다.
3. **자정.** 변경 시각 기준 조회(`searchdtCode=E`)는 예정 시각이 전날 23시대인 편을 당일 결과에 넣을 수 있다. 시각 필드의 날짜를 따른다.
4. **한도 헤더.** `x-ratelimit-limit` / `x-ratelimit-remaining`. 리셋 시각 헤더는 없다. 인천 운항 현황은 출발·도착이 각각 500, 일정은 각각 1,000. 한국공항공사 실시간 조회는 출발·도착이 5,000을 같이 쓰고, 스케줄·검색은 각각 5,000이다. 초기화 시각은 한도를 소진하지 않아 확인하지 않았다.

## 2. 조회 주기

| 구간 | 주기 | 사용 API |
|---|---|---|
| 등록 시 | 1회 | 일정 또는 운항 현황 |
| ~ D-3 | 하루 1회 | 일정 (존재·시각 변경 확인) |
| D-3 ~ 출발 6시간 전 | 1시간마다 | 운항 현황 |
| 출발 6시간 전 ~ 도착 + 1시간 | **15분마다** | 운항 현황 |
| 이후 | 중지 (`phase = done`) | |

- 도착 시각을 모르면 출발 + 6시간을 도착 + 1시간 대신 쓴다.
- 결항이 확정되면 출발 시각이 지난 뒤 중지한다.
- `trackerCount`가 0인 항공편, 한국 공항이 없는 항공편은 조회하지 않는다.
- 한국공항공사 게이트는 출발·도착 **당일**에 `flight-status/info`를 같은 주기로 추가한다. 그 전 시각·결항은 `/arrival`·`/depart`다.

## 3. 예약 함수

Cloud Scheduler 무료 작업 3개 안에서 운영한다.

| 함수 | 주기 | 하는 일 |
|---|---|---|
| `pollFlights` | 15분마다 | `nextPollAt`이 지난 항공편 조회 → 변경 감지 → 알림 → Live Activity 시작·갱신 |
| `dailyCleanup` | 매일 04:00 (일본 시간) | 지난 이력·미사용 항공편·호출 기록 삭제 |

### `pollFlights` 처리 순서

```
1. nextPollAt ≤ 지금인 flights 조회
2. (공항, 날짜, 출발/도착) 묶음으로 공공 API 호출
3. 응답을 정규화해 기존 값과 비교
4. 바뀐 항목 저장 (source = airport_data)
   - 공항 데이터 값이 생기면 그 항목의 사용자 제보 값을 덮어쓴다 (API 우선)
5. 변경 알림 대상 변경이면 등록 사용자에게 FCM 알림 (사용자 언어로)
6. 진행 중 Live Activity가 있으면 갱신 푸시
7. 출발 3시간 전 구간에 들어온 항공편 → Live Activity 시작 푸시
8. 다음 nextPollAt 계산
```

## 4. 변경 감지

| 변경 | 알림 |
|---|---|
| 출발 예정·변경 시각이 **5분 이상** 바뀜 | 출발 시각 변경·지연 |
| 상태가 결항으로 바뀜 | 결항 |
| 출발 터미널 바뀜 | 터미널 변경 |
| 출발 게이트 `null` → 값 | 게이트 배정 |
| 출발 게이트 값 → 다른 값 | 게이트 변경 |
| 도착 시각이 5분 이상 바뀜 | 도착 시각 변경 |
| 수하물 수취대 `null` → 값 | 수하물 수취대 |

- 한 번의 조회에서 여러 변경이 생기면 **알림 하나로 묶는다.**
- `airport_data` 값이 사라지는 경우(값 → `null`)는 알리지 않고 마지막 값을 유지한다. (API 일시 누락 대비)
- 사용자 제보로 생긴 변경은 감지 대상이 아니다.

## 5. 알림 발송

| 종류 | 보내는 곳 | 방법 |
|---|---|---|
| 변경 알림 | 서버 | FCM. 사용자 `notify.changes`가 켜진 경우만 |
| 임박 알림 | 앱 | 로컬 알림 예약 |
| Live Activity 시작 | 서버 | FCM + `liveActivityStartToken`. `liveActivityEnabled`인 경우만 |
| Live Activity 갱신·종료 | 서버 | FCM + `liveActivityUpdateToken` |

### 임박 알림 예약 (앱)

- 앱 실행, 항공편 변경 감지(Firestore 구독), 설정 변경 때마다 **전체를 다시 예약**한다.
- 기준 시각: 변경 시각이 있으면 변경 시각, 없으면 예정 시각
- iOS 대기 알림 64개 제한 때문에 **가까운 항공편부터 최대 60개**만 예약한다.
- 결항 항공편, 이미 지난 시점은 예약하지 않는다.
- 앱이 오래 실행되지 않으면 시각 변경이 반영되지 않을 수 있다. 이 경우에도 서버 변경 알림은 간다.

### 위젯 데이터 (앱)

- Firestore 구독으로 항공편이 바뀌면 다가오는 항공편 요약을 App Group에 저장하고 위젯 갱신을 요청한다.
- 위젯은 D-Day 계산용 타임라인을 자정마다 넘겨 둔다.

## 6. 호출 한도 보호

공공 API 일일 호출 수를 `system/quota_{날짜}`에 센다.

| 사용률 | 동작 |
|---|---|
| ~ 80% | 정상 |
| 80 ~ 95% | `hourly` 구간을 3시간마다로 늘린다 |
| 95% ~ | `frequent` 구간(출발 6시간 이내)만 조회. 새 검색은 `resource-exhausted` |

실패 시 다음 주기에 다시 시도한다. 연속 2회 실패하면 앱이 '확인 실패'를 표시한다.

## 7. 호출량 추정

묶음 조회가 되므로 한 공항·날짜·출발/도착은 조회 주기마다 **1회**다. 같은 날 인천 출발 항공편이 여러 편이어도 출발 호출은 1회다.

| 키 | 일일 한도 (헤더, 2026-10-12) |
|---|---|
| 인천 운항 현황 출발 / 도착 | 각 500 (개발), 운영 신청 시 100,000 |
| 인천 일정 출발 / 도착 | 각 1,000 (개발) |
| 한국공항공사 실시간 조회 | 5,000 (출발·도착 공유) |
| 한국공항공사 스케줄, 검색 | 각 5,000 |

개발 키 500으로도 인천 하루 전체를 15분 간격으로 돌릴 여유는 있다. 출시 전에는 운영 한도를 신청한다. 한도 소진 시 동작은 6절을 따른다.
