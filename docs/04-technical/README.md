## 결정 사항 (2026-10-12)

| # | 결정 |
|---|---|
| TD-01 | 앱·서버 코드를 **새로 작성**한다. 기존 코드는 참고만 한다. |
| TD-02 | 앱: **SwiftUI + @Observable MVVM** + Repository |
| TD-03 | 읽기는 앱이 Firestore 직접 구독, **쓰기는 모두 서버 함수 경유** |
| TD-04 | Firebase 지역 **서울 asia-northeast3** (Firestore 지역은 변경 불가). 2026-10-12 도쿄에서 변경: 한국 공공 API와 가까움. Cloud Functions 가격 등급은 Tier 2(도쿄보다 약간 비쌈) |
| TD-05 | 서버: **TypeScript**, Cloud Functions 2세대, Node.js 22 |
| TD-06 | 공공 API 조회: 등록 1회, D-3 전 하루 1회, D-3부터 1시간마다, **출발 6시간 전부터 15분마다** |
| TD-07 | 지난 항공편은 **사용자가 지울 때까지** 보관 |
| TD-08 | 제보 이력은 출발 30일 후 삭제, 계정 삭제 시 작성자 정보만 제거 |
| TD-09 | 같은 항공편은 **실제 운항 편명 기준 문서 하나**를 모든 사용자가 공유 |
| TD-10 | 시각은 UTC + 공항 시간대로 저장 |
| TD-11 | 공지사항(`notices`)·최소 버전(`config/app`)은 운영자가 Firebase 콘솔에서 입력. 앱은 로그인 없이 읽기만 |
| TD-12 | 화면 모드·공지 읽음 여부는 기기에만 저장 |
| TD-13 | 공항 기본 데이터는 **OurAirports**(Unlicense). 시간대는 IANA ID를 미리 계산해 넣는다. 한·일 이름은 한국·일본 주요 공항만 직접 작성하고 나머지는 영문명 |
| TD-14 | 앱 안 언어는 `\.locale`로 즉시 전환한다. `AppleLanguages`는 쓰지 않는다. 위젯·로컬 알림은 App Group의 언어 코드를 쓴다 |
| TD-15 | 한국공항공사 게이트는 `flight-status/info`로 받는다. D-3~D+6 시각·결항은 `/arrival`·`/depart`. 터미널은 필드가 없어 사용자 제보. `/detail`은 갱신에 쓰지 않는다 |
| TD-16 | 정보 항목에 `previousValue`를 둔다. 공항 데이터로 바뀐 값의 `변경` 칩(24시간)에 쓴다 (M2, 2026-10-12) |
| TD-17 | 알림 설정 구조 변경: `users.notificationsEnabled`(전역) + `trackedFlights.notify`(항공편별 4종, 기본 켜짐). 시점은 고정이라 저장하지 않는다. 새 함수 `updateFlightNotify` (M2 검토, 2026-10-12) |

## 기본값으로 정한 항목 (확정, 운영하며 조정 가능)

| 항목 | 기본값 |
|---|---|
| 사용자별 한도 | 검색 시간당 30회, 다가오는 항공편 30편, 제보 하루 50회 |
| 시각 변경 알림 기준 | 5분 이상 바뀔 때 |
| 확인 실패 표시 기준 | 연속 2회 실패 |
| 정리 함수 실행 시각 | 매일 04:00 (일본 시간) |

## M1 검증 (2026-10-12)

| 항목 | 결과 |
|---|---|
| 공공 API 묶음 조회 | 된다. 인천 하루 전체(출발·도착 각 1,200건 안팎)가 호출 1회. 자세한 내용은 [데이터 갱신](data-sync.md) |
| 코드쉐어·자정·한국공항공사 게이트 | 코드쉐어는 운항 편명으로 합친다. 시각 필드의 날짜를 쓴다. 게이트는 `flight-status/info`. 터미널 필드는 없다 |
| 앱 안 언어 전환 | `\.locale`로 재시작 없이 바뀐다. [전체 구조](architecture.md) |
| 공항 기본 데이터 | OurAirports. 시간대·한·일 이름은 원본에 없다 |
