# 테스트 전략

## 1. 테스트 종류

| 종류 | 대상 | 도구 | 실행 위치 |
|---|---|---|---|
| 앱 단위 테스트 | Domain 계산 (D-Day, 현지 시각, 상태, 정보 항목 상태, 임박 알림 시각), ViewModel | Swift Testing (Xcode 기본) | 로컬 |
| 서버 단위 테스트 | 입력 검증, 응답 정규화, 변경 감지, 조회 주기, 한도 보호, 알림 문구 | `node:test` (Node.js 기본) | 로컬 + CI |
| 서버 통합 테스트 | 서버 함수 + Firestore | Firebase 에뮬레이터 | 로컬 + CI |
| 보안 규칙 테스트 | Firestore Security Rules | Firebase 에뮬레이터 + `@firebase/rules-unit-testing` | 로컬 + CI |
| 화면 확인 | 모든 화면 흐름과 상태 | `DFlight-Mock` + 시뮬레이터 | 로컬 |
| 실기기 확인 | 로그인, 푸시, 로컬 알림, 위젯, Live Activity, App Attest | 본인 iPhone (다이내믹 아일랜드 있음) | 수동 |
| 실제 데이터 확인 | 공공 API 실제 응답으로 등록·갱신 | Debug 빌드 + 개발 Firebase | 수동 |

> Flutter 비유: 앱 단위 테스트는 `flutter test`, Mock 빌드 화면 확인은 가짜 Repository를 주입한 `flutter run`, 실기기 확인은 실제 기기에서 하는 수동 QA다.

## 2. 무엇을 자동으로 테스트하나

**반드시 자동 테스트** — 틀리면 사용자가 비행기를 놓치거나 보안 문제가 생기는 부분

| 영역 | 이유 |
|---|---|
| D-Day·현지 시각·날짜 차이 계산 | 시차·자정 경계에서 틀리기 쉽다. |
| 정보 항목 상태 판정 | 미정 / 자동 정보 없음 / 확인 실패를 잘못 보여 주면 혼란 |
| 변경 감지와 알림 묶음 | 알림 누락·중복 |
| 조회 주기·한도 보호 | 호출 한도 소진 |
| 입력 검증 (서버) | 장난 제보·잘못된 데이터 |
| Security Rules·서버 권한 검사 | 다른 사용자 데이터 노출 |
| 임박 알림 예약 계산 | 시각 변경 반영, 64개 제한 |

**수동 확인으로 충분** — 화면 배치, 문구, 애니메이션

## 3. 테스트 데이터 규칙

- **가상 데이터만** 저장소에 넣는다. 실제 API 응답, 실제 여행 정보, 예약번호는 커밋하지 않는다.
- 가상 항공편은 존재하지 않는 형식을 쓴다. 예: 항공사 코드 `XX`, `YY`
- 공공 API 응답 형식은 M1에서 확인한 **필드 구조만** 따라 가상 응답 파일을 만든다.
- Mock 빌드의 샘플 항공편은 `샘플 데이터` 표시를 유지한다.

## 4. CI (GitHub Actions)

| 작업 | 실행 시점 |
|---|---|
| 서버 빌드 + 단위 테스트 | 푸시, PR |
| 에뮬레이터 통합·보안 규칙 테스트 | 푸시, PR |
| 비밀 정보 검사 (키·토큰 패턴) | 푸시, PR |

- CI에는 실제 키를 넣지 않는다. 테스트는 에뮬레이터와 가상 응답만 쓴다.
- iOS 앱 테스트는 로컬에서 실행한다. 마일스톤 완료 전에 반드시 통과시킨다.

## 5. 실제 데이터 확인 방법

비행 일정이 없어도 확인할 수 있다.
- **오늘·내일 인천 출발 실제 항공편**을 아무거나 등록해서 게이트 배정·변경·지연이 갱신되는지 지켜본다.
- 확인 결과는 문서에 '확인함'과 날짜만 남기고, 실제 편명·응답은 남기지 않는다.

## 6. 베타 테스트

TestFlight 외부 테스트는 하지 않는다. **본인 기기와 본인 여행**으로 확인한다.
- 출시 전 최소 1회는 실제 탑승 항공편(인천 포함 노선)으로 처음부터 끝까지 사용해 본다. (권장, 필수 아님)
